# 运营记录工具发现与调用入口改进

更新时间：2026-08-27 09:06:51 +08:00  
执行工具／模型：Codex (GPT-5.6 Sol)

## 结果

现有正式记录器`scripts/content_operations_cycle.py`没有被替换，也没有新增第二套状态机。此次补齐的是Agent发现与调用入口：用户一旦报告“已经定时／已经发布／当前播放点赞评论收藏／平台警告或诊断／去标识化互动或经营事件”，Agent必须先发现直接运营记录能力，不能只在对话中分析数字。

机器入口：

```text
python scripts/self_media_agent.py operations
```

该命令返回正式记录器、全部固定写入命令、正式快照时间窗、48小时以前的临时观察处理方式和禁止外部操作的边界。`doctor`同时检查短发现文档和全局`tool-registry.json`是否仍暴露这组入口；任一入口丢失即失败关闭。

## 触发与顺序

1. 人工报告已经发布：立即准备受治理的`record-publication`输入并写入私有追加式运营库。
2. 人工报告不足48小时的数据：标记为临时观察，不能伪装成`early`；保证发布事件已经记录，并返回48—72小时的下一正式采集窗口。
3. 48—72小时：使用`record-snapshot`记录`early`。
4. 156—180小时：使用`record-snapshot`记录`d7`。
5. 互动、人工线索判断、实验、诊断、资源、收入、连续性或安全事件：选择记录器已有的同名固定命令。
6. 每次写入后运行`validate-store`。只有私有运营库已经存在并且用户要求复盘，才选择`publication_feedback_review`。

## 变更说明

- 意图：消除“工具已经存在，但Agent面对真实发布数据时没有发现，结果只留在聊天记录”的断点。
- 决策：把运营事件设为五条内容工作流之前的直接触发器，并提供机器可读的`operations`能力；不增加第六条内容创作Recipe。
- 理由：发布、数据快照和互动是运营事实写入，不是内容创作任务，也不是复盘本身。把它们继续藏在`publication_feedback_review`后面会导致时序错误。
- 证据：`self_media_agent.py operations`和`doctor`通过；21项入口聚焦测试通过；`content_operations_cycle.py check`完成12条合成追加记录、独立双跑字节稳定；全局自媒体合同检查通过；`local-tools discover content-creation-system`已显示新增命令。
- 生效范围：Codex和其他从`tool-registry.json`、内容创作系统发现文档或自媒体`AGENT_DISCOVERY.md`冷启动的Agent。不会自动打开平台、抓取数据、发布、联系客户或写CRM。

## 当前真实数据状态

这次改造没有把聊天中的真实账号数据擅自写入运营库。正式写入仍需要对应的账号／内容引用、来源哈希和适用的人工隐私复核凭据。缺项时Agent必须列出准确缺项，而不是伪造凭据或把12小时数据冒充48—72小时正式快照。

## 回滚

可单独回退`self_media_agent.py`的直接能力、Manifest／Registry入口、发现文档和聚焦测试；不得删除或改写任何已经存在的追加式运营库、日志或派生head。
