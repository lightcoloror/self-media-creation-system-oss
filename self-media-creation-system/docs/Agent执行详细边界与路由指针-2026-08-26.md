- 只要用户报告“已经定时／已经发布／现在有多少播放点赞评论收藏／收到平台警告或诊断／出现去标识化互动或业务事件”，先运行`python scripts/self_media_agent.py operations`发现直接运营入口。不得只在对话里分析而不检查是否应落库。
- 这类报告先走直接运营记录，不是第六条内容创作工作流：发布后立即使用`record-publication`；48—72小时使用`record-snapshot + early`；156—180小时使用`record-snapshot + d7`；其他事件选择工具已经提供的同名固定命令。每次写入后运行`validate-store`。
- 48小时之前的12小时／24小时数字只能作为临时观察，不得冒充`early`正式快照。先保证发布事件已记录，再明确下一次可正式采集的起止时间；如缺少隐私复核凭据、权威内容／账号引用或其他必填项，返回准确缺项，不能自行补造。
- `publication-feedback-review`只在现有私有运营存储上运行`build-review`。发布、早期／第7天快照、去标识化互动和人工线索判断分别使用固定命令，一条命令只生成一份回执。
- 图文或视频系列允许一次拍完、一次全部剪完，不强制后续条目保留粗剪。每条仍应作为独立正文／成片冻结，在实际人工发布前单独确认标题、封面和开头。普通反馈只需调整未发布条目的包装；只有发现事实、隐私、合规或重大理解问题时才重新剪辑成片。正文／成片或包装变化后，旧回执失效。
- 不手工修改运营日志或派生head。旧`publication_feedback_tracker.py`只是合成回归依赖，不是正式入口。
- 运营存储先运行`validate-store`。只有派生`head_drift`可以运行`rebuild-heads`；日志、锚点、源哈希、权限或合同漂移必须保留现场并恢复可信副本。

## 视频人工审核

- 视频审核默认代理优先，完整分辨率素材只在代理／关键帧不足时打开。
- 每个审核请求必须绑定候选哈希和准确时间段，同时给出秒数及`MM:SS.mmm`。问题窗口默认前扩2秒、后扩3秒；超过15秒时拆分。
- 默认提供原候选加时间点，不额外生成审核小片段。只有用户明确要求或源文件无法可靠跳转时，才生成独立审核片段。
- 所有基于时间段的视频审核统一进入VKP `targeted-review`。自媒体系统负责问题、哈希、时间范围、播放模式和失效判断；VKP负责切换素材、精确跳转、范围末尾暂停、决定采集和本地回执。
- 文字事实和脚本审核留在写作流程；需要在渲染视频中判断的事项才进入VKP。
- 标准接口：`review_interface={tool_id: video-knowledge-pipeline, surface: targeted-review, delivery: source_time_range_manifest}`。
- 换源、打码、重合成、重构图或局部返工后，先运行 `<workspace>\scripts\video-window-motion-gate.ps1` 比较改动窗口的源片与成片静帧事件。人物窗口新增 `>=0.75 秒` 冻结时失败关闭；合法截图停留必须在视觉计划中预先声明，再把疑点秒数交给 VKP。

## 人物方向、身份和面部处理

- 先检查实际保存的文件并记录哈希绑定的`person_orientation_decision`。自拍预览不能证明保存文件是否镜像。
- 人物方向必须在裁剪、重构图、身份绑定、人脸跟踪、打码、动效、字幕、水印和封面抽帧之前锁定；后来改变方向会使所有空间检查失效。
- 逐人记录角色、身份参考、声音处理和面部处理，并绑定EDL、说话人段、人脸轨迹、实际可见窗口、打码／声音／动效清单。
- 人脸检测只证明画面出现人脸，不能证明该人是客户。没有人工确认身份绑定的人脸不得作为客户打码目标。
- `undecided`只允许生成`internal_preview_only`，不能授权发布。
- 每个打码候选都要对最终画面可见窗口检查：进入前非目标帧、第一帧、中点、最后一帧、退出后非目标帧。目标脸必须全部覆盖，非目标脸不得误伤；同一轨迹不得分配给多个人。
- 授权提示的可见窗口必须与客户面部处理窗口一致。缺失、过期、错人、漏窗口或误伤证据一律阻断。
- 客户效果确认必须绑定精确的处理决定和候选哈希。晚期修改只重做列明的窗口，其他窗口冻结并复用原配方。
- 局部打码或换源返工不能只验“能解码、时长一致、音频一致”；还必须验证修改窗口持续运动，并逐帧检查真实切镜前后，防止动态客户片段被误合成为静态截图。
- 声音转换默认同性别、相近音高范围，并尽量保留F0和韵律；跨性别版本只作为技术试验。

## 标题、封面和拍摄素材

- 标题封面是`handoff-video-owner`内部的有界子路线。使用`video-title-cover build`和`title_cover_candidate_spec.v2`从完整公式池选择2—3个内容匹配候选。
- A／B／C只是测试槽位，不固定代表某三种公式；多样性只是同分时的次级标准。
- 各平台硬长度限制和推荐区间由`video-title-cover`所有者维护。封面Skill和渲染器不得复制另一套标题政策。
- 每个候选都要绑定正文承诺、开头兑现和证据。拍摄前先决定真人主导或证据主导；真人主导使用`templates/真人视频封面专用拍摄清单模板.md`拍摄横竖独立照片。
- 系列内每条正文／成片和包装都必须能独立成立。除不得在标题和封面出现“第1集／第二期／EP03／Episode 3／Part 3”等顺序标记外，冻结内容还必须实际包含本条的受众问题、必要上下文、两个以上按内容顺序出现的信息推进、核心回答和本条回报，并明确不依赖上一条或下一条才能理解。标题、封面和开场必须是同一个承诺；保险内容需人工选择“生活情境先行”或“搜索意图直接回答”，不机械要求保险一律晚出现。`content_diagnosis.py`先阻断“接上期／下期揭晓”等显式依赖，`content_packaging_review.py`再把受众路径、四项锚点、进展顺序和依赖标志绑定到冻结正文哈希；`xhs-evidence-graphic` 和 `case-video-candidate` 都在制作交接前消费该回执，统一 `check_self_media_contracts.py` 会执行该门。“第1步”等单条内部操作步骤，以及本条已兑现后对另一个独立问题的预告，仍允许。

## 字号、最终布局和视觉门禁

- 所有带文字的视觉交付必须使用权威、哈希绑定的字号政策，并对精确成品返回实际渲染证据。
- HTML读取computed style；Remotion／视频绑定渲染值并检查渲染帧。设计声明、设计评分或全尺寸截图不能代替实际证据。

## 真实案例治理

- 金额使用`case-financial-facts.v1`区分收费项目、就诊总费用、实际支付、理赔、周转资金、借款和归还；脚本按场景引用，不要求逐句事实编号。
- 源语言与显示语言不同时，使用`localized-subtitle-review.v1`；普通话译文继承原声话语时间，翻译文本不能反向决定时间轴。
- 使用`artifact-lifecycle-manifest.v1`保护原素材、已审核源、精剪和锁定母版。删除入口只输出`quarantine_only`计划。
- `platform-publication-package.v1`仅保留为旧包兼容校验。新发布路线使用`platform-publication-package.v2`：上传前运行`publication_release`，绑定最终视频、客户隐私门、客户终版确认、机构批准、账号操作者、平台包装和当前账号／作品纠错路线的范围哈希；人工上传后运行`publication_post_upload`，复核实际平台成片的播放、声音、字幕、封面、隐私和元数据。两者都不得自动上传、换源、删除或发布。
- 发布前到上线后的十二步顺序、AI／确定性工具／人工分工、变更失效范围和换源／删除重发规则，统一读取`quality-gate-playbook.md`，不在发现入口再复制一份。
