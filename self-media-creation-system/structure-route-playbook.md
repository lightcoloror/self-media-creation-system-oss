# 内容结构路线库与人工改道规则

> 状态：v1.0 人工可改道操作卡
> 更新时间：2026-08-13 23:45:18
> 执行者：Codex（GPT-5.6 Sol）
> 适用范围：选题确认后到成稿审核前的展开方式选择

## 先分清三个层次

- `content_job`：这篇内容要完成什么任务，例如问答、案例、机制解释或建立信任。
- `structure_route`：这篇内容怎样展开，属于可选的论证或叙事路线。
- `format`：读者怎样消费它，例如图文笔记、短视频或长文。

三者不能互相替代。同一个问题可以用不同结构，同一种结构也可以改造成不同格式。结构路线不是账号固定模板，也不是平台模板。

## 单篇结构路线库

```yaml
structure_route: direct-answer | decision-reframe | scenario-branch | gap-diagnosis | tradeoff-comparison | case-review | mechanism-explanation | tool-action | boundary-map | story-arc | opinion-argument | custom
structure_route_note: 选择理由；custom 时写清自定义展开顺序
```

| 路线 | 什么时候用 | 最小展开顺序 | 常见误用 |
|---|---|---|---|
| `direct-answer` 直接回答 | 问题准确且答案相对明确 | 答案 → 条件/证据 → 边界/下一步 | 为显得专业另造“真正问题” |
| `decision-reframe` 决策重构 | 表面问法遗漏关键前提，直接是/否会误导 | 短答原问 → 指出遗漏 → 判断方法 → 一个决定 | 借重构答非所问或讲成同行课 |
| `scenario-branch` 情境分支 | 答案取决于少数可识别情境 | 共同前提 → 2–4 类情境 → 各自判断 → 自测入口 | 分支太多，变成条款大全 |
| `gap-diagnosis` 缺口诊断 | 读者知道产品，却不知道自己缺什么 | 已有条件 → 风险/目标 → 缺口 → 优先级 → 下一步 | 先推产品，再倒推缺口 |
| `tradeoff-comparison` 取舍比较 | 两个或多个选项不能只看“哪个好” | 同一决策 → 比较维度 → 得失 → 适合谁 → 选择条件 | 参数堆砌，没有现实选择 |
| `case-review` 案例复盘 | 有真实服务过程或决策节点 | 背景 → 关键节点 → 当时判断 → 结果 → 可迁移经验/边界 | 把个案结果写成普遍承诺 |
| `mechanism-explanation` 机制解释 | 需要说明“为什么会这样” | 现象 → 因果链 → 证据 → 反例/边界 → 启示 | 术语过多，结论先于证据 |
| `tool-action` 工具行动 | 读者需要马上检查、计算或办理 | 使用场景 → 输入 → 步骤 → 输出 → 失败条件/求助点 | 只有清单，没有适用范围 |
| `boundary-map` 边界地图 | 主题最容易因相邻概念混淆 | 中心对象 → 包含/不包含 → 例外 → 常见误区 → 去哪里确认 | 为完整而罗列冷门例外 |
| `story-arc` 故事弧线 | 重点是经历、选择、变化与信任 | 处境 → 触发 → 选择 → 变化 → 余味 | 硬塞知识点或标准 CTA |
| `opinion-argument` 观点论证 | 需要表达立场并允许讨论 | 立场 → 依据 → 反方最好理由 → 代价/边界 → 结论 | 只表达态度，没有依据和代价 |
| `custom` 自定义 | 现有路线都不贴合 | 在 `structure_route_note` 写清顺序 | 用 custom 逃避结构判断 |

一篇通常只选一条主路线。局部可以借用另一条路线的一个模块，但不要把多条路线全部叠加成“集大成”。

## 快速路由

```text
问题准确、答案明确？ → direct-answer
答案明显取决于几类人或几种情境？ → scenario-branch
表面问法会把人带向错误决定？ → decision-reframe
读者不知道自己缺什么？ → gap-diagnosis
正在两个或多个方案之间选？ → tradeoff-comparison
有真实服务过程与判断节点？ → case-review
核心在解释为什么？ → mechanism-explanation
读者需要立即完成一项任务？ → tool-action
主要困难是概念或责任边界混乱？ → boundary-map
价值来自真实经历与变化？ → story-arc
价值来自有依据的立场？ → opinion-argument
都不贴合？ → custom，并写选择理由
```

这是一组启发式问题，不是互斥算法。冲突时以本篇的 `primary_goal` 和读者读完要完成的任务为准。

## 与问答分流的关系

`question_structure_route` 继续只判断一件事：原问题可直接回答，还是必须先重构。它不是完整的正文路线库。

- 原问题准确，但答案因人而异：`question_structure_route: direct-answer`，`structure_route: scenario-branch`。
- 原问题准确，但读者需要查缺口：`question_structure_route: direct-answer`，`structure_route: gap-diagnosis`。
- 原问题本身会误导决定：两者都可选 `decision-reframe`。
- 案例、故事、机制和观点不是问答题：`question_structure_route: not-applicable`，再选择对应 `structure_route`。

## 系列拆解是规划路线，不是单篇结构

当一个题目包含多个独立决定、多个特殊人群或多个证据任务时，使用：

```yaml
planning_scope: series
series_question: 整个系列回答的大问题
current_piece_decision: 本篇只解决的一个问题
next_piece_candidates: []
```

系列中的每一篇仍须单独选择自己的 `content_job`、`structure_route`、受众、目标和边界。不要用“系列”作为单篇塞入过多内容的理由。

## 人工可在任意阶段改道

不需要统一界面。以当前内容对象和路由卡为准，人工可在选题、研究、提纲、初稿或终审阶段修改任意路线字段：

```yaml
manual_route_override:
  stage: topic | research | outline | draft | review
  from: 原路线
  to: 新路线
  reason: 为什么新路线更符合读者任务或现有证据
  changed_by: human
```

改道后只重跑受影响的环节：

- 改 `structure_route`：重做提纲、标题承诺与结构质量门；事实台账通常保留。
- 改 `content_job` 或核心决定：回看选题与研究问题，确认现有证据是否仍足够。
- 改受众或范围：重新检查专业距离、例外边界、隐私和医疗保险质量门。
- 改格式或平台：保留事实底座，重新走格式适配器和平台 overlay。

Agent 可以提出路线建议并生成初稿，但人工修改具有最终优先级；修改不自动触发发布，也不覆盖已冻结或已发布版本。

## 观众路径

2026-11-05，Codex（精确运行型号未独立核验）。复用现有字段与检查，不新增审批或强制商业目标。

- 写稿前：在已有 `goal_audience`、`promise` 中确定主要服务传播、信任、行动还是体验；沿用绑定的目的/受众来源。证据复用 `facts`、`materials`，不另建观众卡。
- 写稿及审核：用现有 C01/C03/C04/C08 的理由、正文锚点和 issues 判断相关性、承诺兑现、实际推进与行动顾虑。不同引文不自动证明新信息，审核记录完整不等于内容成立。
- 故事检查事实支持的选择、因果与变化；说明/问答检查答案、证据及边界；工具演示检查输入、过程、结果与失败条件；体验检查选定的感官或实用收益，不强加冲突或答案；技术返工只检查受影响部分。
- 写作和返工时，先补会影响理解的实质缺口，包括关键事实、真实细节、判断过程、必要证据与承诺兑现。文字清楚自然即可保留。先修听不清的人声、字幕错误和看不清的证据。定位到一句或一个时间段的问题，优先局部补录或修改。日常衣着、素颜、普通背景和轻微停顿在不影响理解、隐私或既定要求时可保留。
- 原有必查项完成后，只剩装饰或细微润色建议即可结束当前编辑。仍有效的证据按现有规则复用。关键事实、隐私及作者确认继续按原流程处理，保留理解医疗或保险内容所需的边界。
- CTA 复用既有 interaction/acquisition 的 use/not_used 与理由，不强制获客。服务范围、适用对象、下一步成本在已有说明和检查理由中审查，不新加必填字段。
- 成片复核实际声音/画面，不用计划替代。发布反馈区分传播、消费、信任和业务信号；播放量不能证明转化。
- 反例：标题有答案但正文没有、同一句嵌套截取冒充多次推进，是可机械检查的错误；措辞不同但意思重复、论据不能支持结论、CTA不合适，由现有编辑检查记录，不用关键词打分冒充理解。

顺序：目的/受众与承诺假设 -> 材料及路线选择 -> 正文执行 -> 原有编辑/包装审核 -> 实际制作/落地 -> 人工确认 -> 有实际发布后才观察反馈。冻结后审核是复核，不是此时才决定目的。缺少事实时缩小承诺或保留未知，不补造经历。

### 原有软检查

- [ ] 路线服务于本篇唯一首要目标，而不是因为“这种结构热门”。
- [ ] 开头承诺、正文展开和结尾行动属于同一条主路线。
- [ ] 没有为了完整把所有路线叠加进一篇。
- [ ] 路线需要的证据、案例或输入实际存在；不存在就改道或保留待核。
- [ ] 专业度帮助目标客户判断或行动，没有以复杂度表演权威。
- [ ] 若人工中途改道，受影响的提纲、标题和质量门已经重跑。
